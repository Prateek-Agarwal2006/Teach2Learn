# Running the Phase 1 test bed on the RAG tool

A handoff brief. The fine-tuned portal (`teach2learn-portal/`) has completed the English
half of this and is running the language half; this describes what the RAG implementation
(`LbT (RAG Based) tool Implementaion files-.../`) needs so its results can be placed
beside those rather than merely near them.

Reference implementation for everything below: `teach2learn-portal/scripts/check_languages.py`.
Read it before changing the RAG harness. Most of what follows already exists there.

---

## The one constraint that decides everything

**Any comparative number must be produced by a third component, identical for both
systems, over inputs identical for both systems.**

The two systems' native scores are not comparable and never will be. The portal's adapter
grades itself inline (`Level: Understand / Score: Medium`); the RAG tool has a separate
`scorer_chain` emitting five floats in 0.0–1.0. "Medium versus 0.72" is not a comparison,
and self-grading versus third-party grading is a second confound on top of the scale
mismatch.

What *is* shared, and must stay shared:

| | Status |
|---|---|
| `translation.py` | **Byte-identical.** Re-verified with `cmp` on 2026-09-12, after both sides gained the schema-leak guard. Do not touch it. |
| `lessons.json` teacher scripts | Portal reads it; the RAG harness must be pointed at it |
| Judge model and prompts | **Aligned 2026-09-12.** Same model, same fidelity and fluency prompts on both sides |

Everything comparable flows from those three. Anything else can differ.

### What "the same questions" actually means here

Both systems must receive identical input, but the pipeline has two inputs and only one of
them is currently shared.

| Input | Portal | RAG tool | Shared? |
|---|---|---|---|
| The three teacher sentences | `lessons.json` | `lessons.json` once ported | **Yes** — this is the stimulus |
| The opening question | generated by the adapter | `qa_pool[0]` from retrieval | **No** |

The teacher script is the thing being held constant, and under `--turns 3` both systems
receive the same three sentences in the same order. That is the comparison.

The opening is different in kind on the two sides and cannot be made identical without
disabling retrieval on one and the adapter on the other. Two consequences:

- **In the language sweep it does not matter.** The opening is translated and checked for
  passthrough, but no judged score is computed from it. Fidelity scores the teacher script;
  fluency scores the model's follow-up.
- **In the English sweep it does matter**, because the distinct-question and repeated-opener
  counts include the opening. **Compute the cross-system variety figures over follow-ups
  only**, and say so. Report the with-opening figure separately if useful within a system,
  never across the two.

A third input differs and cannot be normalised away: **the student prompts**. The RAG
student is told *"Always show appreciation… Assume the explanation was helpful enough for
now"* and returns no question when satisfied; the portal's adapter is fine-tuned to always
ask. Question-rate and engagement therefore split on prompt wording rather than capability.
Either normalise the prompts before running, or report those two metrics as a design
difference and exclude them from the quality comparison. Do not score them as quality.

## Blockers, in the order they must be cleared

### 1. The corpus does not exist in the repo

`.gitignore` lists `data/` as "Local test fixtures added while verifying the multilingual
/voice port", and neither `data/` nor `vectorstore/` is present. So the one retrieval call
the sweep makes today runs against an ad-hoc fixture nobody else can reproduce.

**Appendix B of the Teach2Learn paper (`Teach2Learn___ILE.pdf`) lists the actual
instructional material** used to build the RAG pipeline, across the same four courses this
test bed uses — Hanly & Koffman, *Let Us C*, Kernighan & Ritchie, Ranade, and the rest.
Ingest those, and record in the results what was ingested. Until that is done, no
RAG-side number describes the deployed system.

Directory layout `ingest.py` expects, one folder per subject, keyed the same way the
portal's subjects are:

```
data/cp/…  data/dsa/…  data/oop_java/…  data/os/…
```

Those folder names become the catalog keys, and the catalog keys must match the `subject`
field in `lessons.json` or lesson selection cannot work.

### 2. `qa_generator.py` crashes on import without `VS_DIR`

```python
VS_DIR = os.getenv("VS_DIR")
CATALOG_PATH = Path(VS_DIR + "/catalog.json")   # TypeError when VS_DIR is unset
```

Give it a default or fail with a message naming the variable. As written the harness dies
at import with a `TypeError` that says nothing about the cause.

### 3. Decide, explicitly, whether retrieval is in the loop

`build_student_chain` returns `(chain, vs)` and **the chain never uses `vs`** — the prompt
template has `{student_memory}` and `{teacher_explanation}` and no context slot. The only
`similarity_search` in the sweep path is in `qa_generator`, producing the opening question,
which is checked for passthrough but never judged.

So today a comparison would measure a fine-tuned adapter against an *ungrounded* general
LLM. That is the opposite of the RAG tool's intended advantage.

Recommended: **wire retrieved context into the student prompt** before running, and record
that this was done. It changes the system under test, so it must be stated, not slipped in.
If time allows, running both with and without retrieval isolates what retrieval actually
contributes, which is a better result than either arm alone.

### 4. Align the fluency judge prompt — DONE (2026-09-12)

The fidelity prompt is already identical. The fluency prompt is not:

| | Text |
|---|---|
| Portal | "You judge one **question** written in {language}… a learner would actually **ask**" |
| RAG | "You judge one **piece of text** written in {language}… a learner would actually **write**" |

The RAG wording is the more careful one — its student agent legitimately returns no
question on `rating="understood"`, so the harness falls back to the reflection text and
"question" would be wrong. **The portal took the RAG wording**, in the system prompt and in the judge's user message
(`{name} text:` rather than `{name} question:`). The portal's sweep had already finished by
then, so its 525 judged turns were re-scored with the aligned prompt by
`teach2learn-portal/scripts/rejudge_fluency.py` — judge calls only, nothing regenerated,
$0.10 measured. 120 of 525 scores moved and the 15/6/1 tier split did not. Original scores
are kept per turn as `fluency_prompt_v1`.

## Harness changes to port

All of these exist in `teach2learn-portal/scripts/check_languages.py`. Port the behaviour,
not the code — the RAG harness has a different architecture underneath.

1. **Read `lessons.json` from the repo root.** Replace the hardcoded `LESSONS` dict.
   Resolution order: explicit `--lessons` path, then `../../lessons.json` relative to the
   project, then **exit**. No fallback bank: falling back emits a file that looks like a
   24-lesson run and is not.
   *Validation differs from the portal's.* The portal checks each lesson through
   `app.topics.topic_selection`. The RAG tool has no fixed catalogue — subtopics are
   generated at runtime by `generate_subtopics` — so validate only that `subject` exists in
   `vectorstore/catalog.json`, and pass `subtopic` through as free text. Ignore `topic_id`.

2. **`--lesson` takes a comma-separated list**, so a run sized to a time budget can name
   exactly the cells it wants.

3. **`--repeat N`.** One run per cell gives a number with no spread and cannot distinguish a
   real difference from run-to-run noise. Confirm the LLM actually samples — if temperature
   is 0, repeats are identical by construction and the printed range is zero while looking
   like measured variance.

4. **Guards.** Refuse to run when a selected lesson is not marked `reviewed` unless
   `--allow-unreviewed`, and stamp the output either way. Both failures otherwise produce a
   complete-looking results file.

5. **Cost buckets.** Charge generation, translation and judge calls to separate totals with
   call counts and seconds. A single wall-clock number cannot be extrapolated: the three
   costs are paid to different places. This is what sizes the full run.

6. **Write results to stdout always**, with `--out` as an additional crash-safety copy
   rewritten after every repeat. The portal learned this the hard way — `--out` alone
   stranded four subjects' results on the remote host.

7. **Provenance stamp.** Record model, bank version and lesson ids, judge model, decoding
   parameters, retrieval on/off, corpus provenance, timestamps, elapsed seconds. This is
   the test-bed table in the write-up; recording it afterwards from memory is how tables
   become wrong.

## The runs

Mirror the portal's two sweeps so the tables line up.

**Sweep A — English.** All 24 lessons, 3 repeats, no translation, no judge. Measures
whether the student agent varies its questions and how it assesses the explanation.

Port `_templated_openers` from the portal harness verbatim. It compares the first six words
rather than whole strings, and on the portal it found that Qwen3 opened 61 of 72 questions
with the same clause while whole-string distinctness read a perfect 1.00 for every model.
Whole-string distinctness alone will mislead you in exactly the same way.

Expect a complication: the RAG student prompt says *"Always show appreciation… Assume the
explanation was helpful enough for now"* and sets `message = null` on `rating="understood"`.
The portal's adapter is fine-tuned to always ask. **Any question-rate or engagement metric
therefore splits on prompt wording, not capability** — report it as a design difference or
normalise the prompts first, but do not score it as quality.

**Sweep B — languages.** Two lessons per subject, one of each pair carried over from
`LANGUAGE_TEST_RESULTS.md`, across all 22 languages, one repeat. The mechanical checks
(untranslated text, script leaks, retries) are the figures to quote; fidelity and fluency
are an independent model's opinion and stay directional until a native reader confirms them.

Sindhi will fail. It failed identically on all four portal adapters, which is what places
the fault upstream in Sarvam rather than in any model. Since `translation.py` is
byte-identical here, it failing again is a check that the boundary is wired correctly, not
a new finding.

**Timing.** The portal measured 5.5s per generation, 1.0s per crossing, 2.9s per judge call,
about 49s per language-run. The RAG tool calls OpenRouter rather than a local GPU, so
expect different figures; run one lesson across two languages first and read the cost
buckets before committing to the full sweep.

## What this costs, and how to stop arguing about it

Two estimates for this run have differed by roughly 200x, so measure rather than argue.
The portal's side is now measured: **1,060 judge calls cost about $0.30 (₹26)**, at roughly
$0.0003 per judge call, read from the OpenRouter credits endpoint before and after a
subject. Sweep A cost nothing on either service, because an English baseline makes no
translation or judge calls at all.

The RAG side differs in exactly one line item: **its student agent runs through OpenRouter
rather than a local GPU**, so it pays for generation that costs the portal nothing. Judge
and Sarvam volumes are identical by construction, since both sides use the same judge and
the byte-identical `translation.py`.

Three things decide the total, and all three must be stated before any figure means
anything:

| | The comparison run | An estimate that would be ~36x higher |
|---|---|---|
| Grid | 8 lessons x 22 languages x 1 repeat = 528 turns | 24 x 22 x 3 = 4,752 turns |
| Agents per turn | `student_chain` only | student + evaluator + scorer + summarizer |
| Model | pinned and recorded | left on the `--model openai/gpt-4o` default |

**The comparison needs the left column.** The evaluator and scorer are the RAG tool's own
internal grading, and its scale is not comparable to the portal's inline `Score: Medium`
anyway -- that is the whole reason an external judge exists. Running them costs four times
as much and produces nothing that can be placed beside a portal number.

Measure it before committing:

```bash
# before
curl -s https://openrouter.ai/api/v1/credits -H "Authorization: Bearer $OPENROUTER_API_KEY"
# one lesson, two languages -- Hindi as a working case, Sindhi as the known failure
python scripts/check_languages.py --sweep --lesson os/threads-scheduling/cpu-scheduling \
  --languages hi,sd --repeat 1 --out calib.json
# after
curl -s https://openrouter.ai/api/v1/credits -H "Authorization: Bearer $OPENROUTER_API_KEY"
```

That is 2 language-runs: 6 generations, 12 judge calls, 20 crossings. The credits delta
divided by those counts gives measured per-call costs, and the full run is then arithmetic
rather than anyone's estimate. The cost buckets the harness prints give the call counts
directly.

## Reporting

`teach2learn-portal/scripts/report_sweep.py` already emits the tables and takes any number
of results files. Point it at the RAG results too rather than writing a second reporter —
one reporter over both systems is itself part of the commensurability argument.

It produces a language-by-subject matrix, a per-language table with ranges, the mechanical
checks, and the English question-variety table. Its status rule is printed above the table
rather than applied silently, and reproduces the classifications in
`LANGUAGE_TEST_RESULTS.md` on that report's own numbers.

## Do not change

- **`translation.py`.** Byte-identical to the portal's. If it drifts, every cross-system
  language number becomes uninterpretable.
- **The teacher scripts in `lessons.json`.** Four are carried verbatim from
  `LANGUAGE_TEST_RESULTS.md` and a test enforces it. Editing one silently breaks the
  comparison against that report on that cell. If a script must change, change it in the
  shared file, set `reviewed` back to `false`, and say so.
- **The judge model.** Same model both sides, or the scores are two different opinions.

## Known difference, recorded not corrected

The portal's language sweep ran at **temperature 0.2**; the RAG sweep ran at **0.25**, which
is what `TEST_BED.md` specifies. Re-running the portal side needs the GPU host, so the
difference is documented in both results files instead. It bears on question-variety and
spread figures more than on the fidelity and fluency means.

## Known imprecision, already accepted

`dsa/trees-heaps/heaps` describes the root as holding the smallest element — true of a
min-heap, stated as though it held for every heap — and carries `2i+1` and `2i+2`, the only
raw arithmetic symbols in the bank. Both are consequences of carrying that script over
unchanged. Documented in `TEST_BED.md`; do not fix them.

## Deliverables

1. A results JSON per subject per sweep, with the provenance stamp populated.
2. `results-english.md` and `results-languages.md` from the shared reporter.
3. A short note recording: what corpus was ingested, whether retrieval was wired into the
   student prompt, which model was used, and the decoding parameters.

Item 3 is what makes the comparison publishable. Without it the RAG numbers describe an
unknown system.
